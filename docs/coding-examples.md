# How to code an episode: a worked guide

This guide goes with `docs/codebook.md`. The codebook is the authority on
columns and allowed values; this guide shows how to apply it.

The four examples below come from the dataset but are **not** in the labeling
sample, so you will not meet them while coding.

## Steps for each episode

1. **Read the evidence first.** Read the commit messages, then open "GitHub
   details" for each commit: the full message, its trailers, the linked pull
   request, and the diff with the detector's matches highlighted. Leave the
   detector's labels hidden until you have answered step 2.
2. **`detector_correct`** (`yes`, `no`). Is this really a migration-related
   episode? A pin below 2 counts: it is a response to the breaking change. If
   `no`, fill only `detector_correct` and `notes`, and leave the rest empty.
3. **`end_state`** (`modern_only`, `dual_era`, `sdk_v2_default`,
   `pinned_below_2`, `still_v1`, `standalone_fastmcp`, `no_official_sdk`,
   `reverted`, `abandoned`). The repository's state **after** the episode.
   Judge it from the diff, not from the repository as it is today.
   `modern_only` needs evidence of legacy removal or a runtime probe; without
   it, prefer `sdk_v2_default`.
4. **`trigger`** (`proactive`, `user_issue`, `bot_pr_breakage`,
   `downstream_change`, `unknown`). Why the work happened. Check linked issues
   and PRs and the first commit message; the "PRs ±14 days" and "Issues ±14
   days" links help. `unknown` is a legitimate answer and is preferable to a
   guess. Each value is defined under "The `trigger` column" in the
   codebook; if more than one fits, the codebook gives the order to choose in.
5. **`author_kind_verified`** (`human`, `bot`, `ai_agent_assisted`). Check the
   PR body and commit trailers (`Co-Authored-By: …`), and the author's account.
   Code `human` only with positive evidence of a human author, and note the
   ambiguity otherwise.
6. **`deprecated`** (blank, or `feature:disposition` pairs). Usually blank. Fill
   it only when the episode touches sampling, roots, protocol-level logging or
   resource subscriptions.
7. **`notes`.** Required when a cell is left empty, when a value was a close
   call, for every `no`, and for anything the columns cannot carry.

## Example 1: a clean migration, written by an agent

**`joshuaosborn561-lang/email-waterfall#0`**: one commit, *"Fix MCP 2.0 server
import and contact email merge."*

| Evidence | What it tells you |
|---|---|
| Diff: `-from mcp.server.fastmcp import FastMCP` and `+mcp>=2.0.0` | A real move from SDK v1 to v2 |
| Message: "Switch the server to mcp.server.MCPServer (v2 has no FastMCP path)" | Now on v2's default API, with no modern features |
| The commit author's account is `cursoragent`, and the PR description contains `CURSOR_AGENT_PR_BODY` | Written by a coding agent, although there is no trailer |
| "Fix … import" wording, no linked issue, and the PR is about something else | Says what was fixed, but not what prompted the fix |

| Column | Value |
|---|---|
| `detector_correct` | `yes` |
| `end_state` | `sdk_v2_default` |
| `trigger` | `unknown` |
| `author_kind_verified` | `ai_agent_assisted` |
| `deprecated` | (blank) |
| `notes` | Committed by the cursoragent account; PR body generated by Cursor. No trailer. Trigger unknown: the fix sits in an unrelated feature PR, with no issue. |

**Why:** `end_state` is `sdk_v2_default`, not `modern_only`, because nothing
shows legacy support was removed. The author is an agent although the commit has
no trailer: always check the author's account and the PR description as well as
the trailers. `trigger` is `unknown` because nothing says what prompted the fix,
and the codebook prefers `unknown` to a guess.

## Example 2: a defensive pin

**`buckg71/whizzard#0`**: pull request #52, *"fix: pin mcp<2 — 2.0.0 removed
mcp.server.fastmcp"*

| Evidence | What it tells you |
|---|---|
| Diff: `+"mcp>=1.0,<2"`, with a comment explaining the pin | A deliberate deferral, so it is migration-related |
| PR description: a fresh `pip install` resolved to 2.0.0 and the server failed with `ModuleNotFoundError`; the problem surfaced during documentation work | The maintainer found the breakage; no user issue, no bot PR |
| Three `Co-Authored-By: Claude …` trailers | Agent-assisted |
| The message leaves "Migration to the 2.x …" for later | The pin is meant to be temporary |

| Column | Value |
|---|---|
| `detector_correct` | `yes` |
| `end_state` | `pinned_below_2` |
| `trigger` | `downstream_change` |
| `author_kind_verified` | `ai_agent_assisted` |
| `deprecated` | (blank) |
| `notes` | Explicitly temporary pin. The break was latent until a fresh install; found by the maintainer, no issue or bot PR. |

**Why:** a pin below 2 is a response to the breaking change, so
`detector_correct` is `yes` even though nothing was migrated. `trigger` is
`downstream_change`: the PR says the mcp 2.0.0 release broke the server, and no
issue or bot PR prompted the work.

## Example 3: pin, then port, on the same day

**`kanishka089/computer-use-mcp#0`**: two commits.

1. *"Fix: pin mcp<2 — every fresh install was broken at import"* adds `mcp>=1.2,<2`.
2. *"Support mcp 2.x and unpin the dependency"* removes the pin and imports
   `MCPServer` in a `try`, falling back to `FastMCP` in the `except`.

| Column | Value |
|---|---|
| `detector_correct` | `yes` |
| `end_state` | `dual_era` |
| `trigger` | `downstream_change` (or `user_issue` if the issues link shows a user report that prompted it) |
| `author_kind_verified` | `ai_agent_assisted` (Claude trailers on both commits) |
| `deprecated` | (blank) |
| `notes` | Pinned, then ported within hours; the episode contains both. Supports both SDK majors through a try/except import. |

**Why:** code the end state from where the episode **ends**. After the second
commit the server runs on either SDK major. So the answer is `dual_era`, not
`pinned_below_2` (where the episode started) and not `sdk_v2_default` (because v1
still works). The pin belongs in `notes`.

## Example 4: not a migration

**`bvisible/mcp-ssh-manager#0`**: one commit, *"fix: report the real package
version to MCP clients + upgrade the SDK"*. The relevant diff:

```
-    "@modelcontextprotocol/sdk": "^1.17.2",
+    "@modelcontextprotocol/sdk": "^1.30.0",
```

This raises the minimum SDK version within v1, to pick up security fixes.
Nothing moved to v2 and nothing was removed: the v1 dependency line was edited.

| Column | Value |
|---|---|
| `detector_correct` | `no` |
| `notes` | v1 minor bump (^1.17.2 → ^1.30.0) for security advisories. The v1 line was edited, not removed. No SDK-major or protocol change. |
| all other columns | (blank) |

**Why:** the detector counts an edited dependency line as both removed and
added, so a version bump within v1 can look like a removal. Check whether the
version actually crosses a major (`<2` → `>=2`) before answering `yes`.

## Quick checklist

- [ ] Read the diff and messages **before** revealing the detector's labels.
- [ ] Is a dependency change crossing the major (1.x → 2.x), or only bumping within 1.x?
- [ ] Is a "fastmcp" match the official SDK (`mcp.server.fastmcp`) or the standalone `fastmcp` package?
- [ ] Is a `create_message` or `sampling` match MCP's, or another LLM library's?
- [ ] `end_state` describes the state after the **last** commit of the episode.
- [ ] Author: check trailers, the author's account, and the PR description.
- [ ] Every `no`, every blank cell, and every close call has a note.
